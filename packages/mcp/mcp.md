# AI surface

How the design system reaches AI coding tools: an MCP server on two transports, an
`llms.txt` on the docs site, and a Claude Code plugin. All three are generated from the
same repo sources, so none of them can drift from the library they describe.

For the consumer-facing view - how to connect and what the tools do - see
[`README.md`](./README.md). This document is the contributor's view.

---

## The pieces

| Piece                                | Lives in                         | Ships via                                     |
| ------------------------------------ | -------------------------------- | --------------------------------------------- |
| MCP server (hosted)                  | `packages/mcp/src/worker.ts`     | Cloudflare Worker at `mcp.soroush.tech`       |
| MCP server (local)                   | `packages/mcp/src/bin.ts`        | `npx -y @soroush.tech/mcp` (npm, public)      |
| `llms.txt` / `llms-full.txt`         | `apps/docs/scripts/emitLlms.ts`  | The docs build, into `build/client`           |
| Claude Code plugin                   | `plugins/soroush-design-system/` | `.claude-plugin/marketplace.json` at the root |
| Shared registry and README splitting | `packages/docs-content/`         | Private workspace package                     |

`@soroush.tech/docs-content` is the seam. It owns the component taxonomy and the
`splitReadme` / `stripReadmeChrome` / `kebabCase` helpers, and `apps/docs/src/common/nav.ts`
re-exports it. The docs site, `llms.txt`, and the MCP server therefore all describe one
library from one registry - which is the whole point of the package existing.

## Content pipeline

`pnpm --filter @soroush.tech/mcp gen` reads the repo and writes
`packages/mcp/src/generated/content.ts`, which both bundlers inline. Nothing is read
from disk at runtime.

| Content           | Source of truth                                                                           |
| ----------------- | ----------------------------------------------------------------------------------------- |
| Component records | `packages/*/src/*/README.md`, split into `intro` / `api` / `examples`                     |
| Token contract    | `baseTheme` in `packages/design-system/src/theme/themes.ts`, imported and serialized      |
| Guides            | `packages/design-system/docs/`, `apps/docs/content/docs/`, `packages/styled-system/docs/` |
| Consumer refs     | `packages/design-system/docs/consumer/`                                                   |

Two consequences worth knowing:

- **A component's README is its API documentation.** `get_component` with `part: "api"`
  returns everything from the README's `## ...Props` heading to `## Examples`. A README
  that loses that heading silently loses its API section - `pipeline.test.ts` asserts
  which components legitimately have none (`Backdrop`, `Toolbar`), so a third one
  appearing fails the suite.
- **A new theme scale needs no change here.** `buildTokens` serializes whatever
  `baseTheme` holds, and a test compares the serialized scale names against the live
  object, so a dropped scale fails rather than disappearing quietly.

Relative links in READMEs (`../View/`) are rewritten to absolute docs URLs by
`absoluteReadmeLinks`, because a caller reading them outside the repo cannot resolve
`../`.

## Generated files, and which are committed

| File                                    | Committed? | Guard                                   |
| --------------------------------------- | ---------- | --------------------------------------- |
| `packages/mcp/src/generated/content.ts` | No         | Regenerated by every build and test run |
| `plugins/**/skills/**/references/*`     | **Yes**    | `pnpm gen:plugin-refs --check`          |

The plugin's references are committed because users install the plugin from git and
never run a build. That makes them driftable, so the check runs in `.husky/pre-commit`
and in CI's lint job. After changing a component README, a token, or anything under
`packages/design-system/docs/consumer/`, run:

```sh
pnpm gen:plugin-refs
```

and commit the result.

## Deploying

The Worker and the npm package are released separately, both manually:

- **Worker** - `CD · MCP (Cloudflare)` (`workflow_dispatch`, main only). It deploys
  whatever main currently documents, since the bundle is baked at build time. Locally:
  `pnpm --filter @soroush.tech/mcp deploy` after `wrangler login`.
- **npm** - the usual `CD · Packages (npm)` dispatch, which gates on
  `packages/mcp/release-notes/<version>.md`.
- **`llms.txt`** - no separate deploy. The docs build emits it into `build/client`, and
  `CD · Docs` composes and ships that tree.

## Testing

`packages/mcp` tests the protocol, not just the renderers: `server.test.ts` drives a
real SDK `Client` over `InMemoryTransport`, and `worker.test.ts` posts JSON-RPC at
`worker.fetch()`. The pipeline tests run against the real repo, so they double as a
lint on the docs sources.

## Gotchas

- **The bin is ESM-only.** Its top-level `await` has no CJS equivalent, so
  `tsdown.config.ts` builds `index` dual-format and `bin` as ESM alone.
- **The bundle is a module, not JSON.** The dts generator cannot trace a `.json`
  import, so `pipeline/emit.ts` renders a typed `.ts` module instead.
- **`vite.config.ts` cannot import `docs-content`.** Vite executes the config in Node
  with workspace dependencies left external, and this package exports TypeScript
  source. That is why `llms.txt` is emitted by a `tsx` post-build script rather than a
  Vite plugin like `sitemapPlugin.ts`.
- **The Worker is stateless.** Each request builds a fresh server and transport, so a
  reused isolate cannot leak one caller's session into another's.
